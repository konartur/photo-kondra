# Послідовний план хостингу й деплою

## Збережене рішення — 2026-11-19

Власник відклав фактичний деплой. Зараз дозволено підготувати документацію; створення платних ресурсів, зміни DNS і запуск публічного середовища не виконуються. Повернутися до виконання після нового доручення власника. Цей документ зберігає порядок роботи між сесіями.

Реалізовувати етапи нижче послідовно. На кожному етапі спочатку перевірити поточний стан, виконати найменші потрібні зміни, пройти критерії й записати результат. Якщо перевірка не пройдена або бракує доступу, зафіксувати блокер; залежний етап залишається невиконаним. Підготовлений конфіг не означає перевірене середовище.

## 1. Зафіксувати реліз і незавершені вимоги

- Прочитати `AGENTS.md`, перевірити робоче дерево й поточні scripts у `package.json` обох застосунків. Зберегти сторонні незакомічені зміни.
- Узгодити склад релізу й зафіксувати commit, що буде розгорнутий. Підготовку інфраструктури вести окремими невеликими змінами.
- Перевірити [матеріали портфоліо](tickets/05-production-portfolio-content.md) та [контактні переходи](tickets/09-portfolio-contact-links.md). Для тестового HTTPS дозволені демо-фото; публічний реліз потребує погоджених фото й обкладинок. Канали без погоджених адрес приховати.
- Підтвердити, чи з'явилися видані приватні URL. За збереженим рішенням це перший публічний запуск, але перед перемиканням факт потрібно перевірити повторно.

**Готово:** визначені commit, склад релізу, незакриті вимоги та статус старих посилань.

## 2. Обрати й описати хостинг

Базова схема з [архітектурного рішення](portfolio-domain-decision.md): один Linux-сервер, Nginx, Next.js і NestJS; PostgreSQL і Redis у Docker Compose; оригінали та ZIP у приватному S3. Зберегти модульний моноліт. Поточний Compose запускає інфраструктуру, а застосунки запускаються на хості.

- Погодити провайдера, регіон, бюджет, доступ оператора до SSH/DNS/TLS/S3 та передрелізний hostname. Публічний домен визначити до фінальної збірки.
- Звірити підтримку Node.js і Docker Compose з [інструкцією стенда](staging-https.md) та lock-файлами. Поточна інструкція очікує Node.js 24+ і Compose 2.24.4+.
- Визначити CPU/RAM/диск через пробний запуск Sharp і ZIP із репрезентативними фото, з урахуванням одночасних задач, збірки, БД, Redis і журналів. Зафіксувати запас і обмеження; ресурси не вважати достатніми без вимірювання.
- Визначити резервні копії, термін зберігання, допустиму втрату даних і час відновлення. Призначити відповідального за оновлення, TLS і збої.

**Готово:** записані погоджені параметри й відповідальні; придбання ресурсів виконується лише в межах окремого доручення.

## 3. Підготувати сервер і запуск процесів

- Підготувати користувача сервісу без root, SSH за ключем, синхронізацію часу й оновлення ОС.
- Ззовні дозволити HTTPS і обмежений адміністративний SSH. HTTP відкривати лише якщо обрана процедура TLS цього потребує. Порти Next.js, NestJS, PostgreSQL і Redis залишити приватними.
- Для поточної схеми встановити `API_HOST=127.0.0.1`, запускати Next.js на `127.0.0.1:3001`; застосувати loopback-публікацію БД і Redis зі staging overlay.
- Додати й перевірити визначення сервісів у менеджері процесів хоста: робочий каталог, production-середовище, автоматичний старт, перезапуск, коректна зупинка і ротація журналів. Не залишати застосунки залежними від відкритої SSH-сесії.
- Перевірити мережеву недоступність внутрішніх портів із зовнішньої машини й автоматичне відновлення сервісів після контрольного перезапуску.

**Готово:** сервіси керовано запускаються та відновлюються, внутрішні порти недоступні з інтернету.

## 4. Налаштувати дані, секрети та S3

- Створити конфіг із `.env.example`; замінити всі демонстраційні паролі й JWT-секрети. Доступ до файлів секретів надати лише потрібним сервісам/оператору; секрети не комітити й не записувати в звіт.
- Узгодити `APP_URL`, внутрішній `API_URL`, `CORS_ALLOWED_ORIGINS`, підключення БД/Redis, ліміти файлів і строки підписаних URL. Звірити змінні з фактичними валідаторами конфігурації.
- Встановити однаковий випадковий `BFF_TRUST_SECRET` для Nginx, Next.js і NestJS за [інструкцією HTTPS](staging-https.md). Для прямого ingress залишити `TRUSTED_PROXY_CIDRS` порожнім; балансувальник потребує окремо перевіреної схеми довіри.
- Поточний Compose не вмикає автентифікацію Redis через `REDIS_PASSWORD`: якщо пароль обрано, налаштувати сервер і клієнт узгоджено та перевірити вхід. Саме заповнення змінної не захищає Redis.
- Використати окремі тестові БД і bucket для стенда. Перевірити приватність S3, мінімальні IAM-права й точний HTTPS-origin у CORS, включно з PUT та `If-None-Match`, за [CORS](production-cors.md) і [аудитом storage](security/storage-private-links-audit.md).
- Запустити `npm --prefix backend run storage:audit` з потрібними правами. `AccessDenied` фіксувати як неперевірений контроль, а не успішний аудит; потрібне окреме підтвердження відповідальної особи.
- Налаштувати резервне копіювання БД поза сервером і захист оригіналів від втрати; перевірити відновлення в ізольоване середовище. Постійний Docker volume сам по собі не є резервною копією.

**Готово:** конфіг валідний, пряме завантаження в приватний S3 працює, контроль відновлення пройдено.

## 5. Перевірити код релізу

На окремій тестовій БД, після встановлення залежностей із lock-файлів і генерації Prisma Client, виконати з кореня:

```sh
npm run lint
npm run typecheck
npm test
npm run test:e2e
npm --prefix backend run test:integration
npm --prefix frontend run test:e2e
npm run build
git diff --check
```

Кореневий `test:e2e` перевіряє backend; Playwright запускається окремо. Інтеграційним тестам надати їхню тестову конфігурацію, PostgreSQL і Redis за поточними інструкціями репозиторію. Production-збірку frontend виконувати з цільовим `APP_URL`. Перевірки запускати для того самого commit і конфігурації релізу; після зміни коду повторити відповідні перевірки. Моки не замінюють приймання на реальному S3.

**Готово:** усі потрібні команди завершилися успішно, збережені дата, commit, результати й обмеження перевірок.

## 6. Розгорнути й прийняти тестове HTTPS-середовище

Виконати команди й налаштування з [інструкції staging](staging-https.md): підняти БД/Redis, встановити залежності, згенерувати Prisma Client, застосувати міграції через `prisma:deploy`, зібрати застосунки, запустити сервіси, перевірити Nginx і TLS. Seed адміністратора запускати лише коли потрібне початкове створення, із секретами середовища.

У двох чистих сесіях (адміністратор і клієнт), включно з телефоном, перевірити:

1. Головну, прямі URL історій, `/login`, `/dashboard`, контакти й адаптивність.
2. Вхід і поновлення сесії через HTTPS, cookie `Secure`/`HttpOnly`, відсутність помилок CORS та mixed content.
3. Створення альбому → прямий PUT у S3 → завершення upload → Sharp → `READY` → приватний URL → grid/preview → оригінал → повний і вибраний ZIP.
4. Відмову за відкликаним/простроченим токеном, недоступність чужих фото й захищені адмінські маршрути.
5. Обробку невдалого upload/обробки/ZIP, повторну спробу й видимість помилок у безпечних журналах. Перевірити 429 та поведінку UI без втрати сесії.
6. Репрезентативний пакет фото: тривалість обробки, пікову пам'ять, диск і стан черг. Зіставити з ресурсами з етапу 2.

**Готово:** є протокол приймання на реальному HTTPS і S3. Непройдений основний сценарій блокує публічний запуск.

## 7. Підготувати production і відкат

- Закрити вимоги матеріалів і контактів з етапу 1. Встановити канонічний HTTPS-origin у runtime-конфіг і збірку frontend; перевірити метадані й `noindex` приватних сторінок.
- Зафіксувати поточні DNS, ingress, реліз і конфіг origin; підготувати попередній працездатний реліз або сценарій вимкнення першого запуску.
- Перед міграціями зробити й перевірити резервну копію. Оцінити сумісність нового schema зі старим застосунком. Відкат застосунку не скасовує міграції: підготувати окрему стратегію БД без втрати нових даних. Руйнівні міграції не виконувати без окремого погодженого плану.
- Налаштувати перевірку доступності HTTPS, помилок API, невдалих/завислих задач, диска, пам'яті, резервних копій і строку TLS. Сповіщення надсилати лише на погоджений канал.
- За наявності раніше виданих URL зберегти їхній HTTPS і маршрут за [правилами сумісності](tickets/07-existing-gallery-links.md).
- Підготувати конкретний план перемикання з цільовим доменом, commit, результатами приймання й умовами відкату. Публічне перемикання виконувати в межах доручення власника на деплой.

**Готово:** відомий порядок перемикання та відкату застосунку/даних, перевірений backup, визначені відповідальні й моніторинг.

## 8. Виконати запуск і перевірити після перемикання

Виконати [фінальний checklist](tickets/08-launch-and-smoke-check.md). Після DNS-переходу повторити сценарій адміністратора і клієнта з етапу 6, перевірити нові й раніше видані URL, канонічний домен, TLS та прямі завантаження з S3. Спостерігати за станом процесів і черг під час контрольного навантаження.

Якщо не працює вхід, upload, доступ за приватним URL, оригінал чи ZIP, зупинити видачу нових посилань і застосувати підготовлений відкат. Після відкату повторити основний сценарій; зберегти доступ за вже виданими URL. Для першого запуску без попереднього релізу вимкнути публічний ingress і повернути попередній DNS, зберігши дані для діагностики.

**Готово:** production smoke-тести пройдені й зафіксовані; інакше запуск має статус невдалого або відкладеного.
