## Межі та правила виконання

1. Перед роботою прочитати [AGENTS.md](../../../AGENTS.md), [hosting/deployment plan](../../hosting-and-deployment-plan.md) і локальні правила змінюваних каталогів. Цей backlog не дозволяє деплой, платні ресурси, DNS/TLS-зміни чи реалізацію оптимізацій. Збережене рішення відкласти деплой чинне. Висновок PERF-08 є вхідним матеріалом до етапу 2 hosting plan, а не виконанням його етапів.
2. Не змінювати бізнес-логіку, DTO, авторизацію, політику rate limiting, алгоритми фото/ZIP чи технологію backend. Дозволена після підтвердження лише тестова інфраструктура й вимкнена за замовчуванням діагностика. Використовувати вбудовані Node.js/ОС засоби; k6 та колектори запускати зовні, без зайвих production-залежностей. Оптимізації — окремі майбутні тікети.
3. Лише синтетичні фото, тестові облікові записи, окремі PostgreSQL/Redis/volumes та окремий приватний non-production S3 bucket. Не читати робочу `.env` автоматично; явна perf-конфігурація, перевірка цільових адрес/ідентичності AWS та відмова від запуску проти production. Cleanup тільки ресурсів конкретного run; без `FLUSHDB`, глобального purge bucket або видалення чужих volumes.
4. Базова топологія: один NestJS-процес із двома BullMQ workers, PostgreSQL, Redis, Next.js BFF і Nginx. S3 — зовнішній. Загальний ліміт **1024 MiB / 1 vCPU** стосується всієї цільової машини; окремо записати, чи тариф провайдера означає 1000 MB. Врахувати ОС, Docker daemon, kernel/page cache, журнали та службові процеси. Варіант без Next.js є лише додатковим backend-only експериментом і не доводить придатність чинного продукту.
5. k6, генерацію fixtures, профайлери й збірку виконувати поза цільовим бюджетом, із явним обліком розміщення. Якщо збірка/backup/міграції мають виконуватися на VPS, виміряти їх окремо: runtime-pass не є build-pass. Локальний MinIO допускається тільки зовні бюджету як окремий емулятор; його результати не прирівнювати до AWS S3. Потрібна перевірка реальним тестовим S3 без створення платних ресурсів у межах цього доручення.
6. До першого навантаження PERF-01 фіксує числовий workload/SLO. Зберігати commit, lock hashes, версії Node/образів/k6, host/VM/kernel/cgroup, конфіг без секретів, seed/manifest fixtures, run ID, UTC timeline і точні команди. Поточні значення з `.env.example` — конфігурація, а не виміряна місткість.
7. У результатах розділяти HTTP latency, queue wait, processing time, end-to-end час і S3 transfer. 202 не дорівнює готовому ZIP; signed URL не дорівнює перевіреному завантаженню. Очікувані 401/404/409/410/429 перевіряти окремо від успішного потоку й не використовувати throttling для приховування недосягнутого навантаження.
8. Кожен тікет при виконанні доповнити командами, артефактами, результатами кожного AC та блокерами. Не комітити JWT, cookies, приватні токени/URL, AWS-секрети, дампи чи сирі логи з такими даними. Метрики HTTP групувати за шаблоном маршруту, без token/photo ID/query labels.
9. Для змін коду/конфігурації виконати застосовні lint, typecheck, unit/integration/E2E і build за AGENTS.md; не запускати build/tests усередині вимірюваного runtime. Для документації — перевірка посилань і `git diff --check`. Відсутня команда або пропущена перевірка має бути явно зазначена.

## Майбутні артефакти

У `docs/performance/` зберігати workload/SLO contract, runbook, опис метрик, результати з посиланнями на знеособлені артефакти, аналіз і фінальний звіт. Скрипти/Compose/k6 розміщувати згідно з чинними conventions після PERF-01. Великі time series, binary fixtures і snapshots не додавати до Git; зберігати manifest/checksum і контрольоване місце артефактів. Зараз створено тільки цей backlog і початкове дослідження.
