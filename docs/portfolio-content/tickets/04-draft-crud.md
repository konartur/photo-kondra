# PF-CONTENT-04 — Редагування напрямів, історій та головної

**Статус:** Реалізація підготовлена локально; приймання відкрите. Тести не запускалися за прямою вказівкою власника. **Область продукту:** лише портфоліо.
**Залежності:** PF-CONTENT-01–03. Порядок і посилання — у [індексі](README.md).

## Мета та область роботи

PortfolioModule admin controllers/service; settings/contacts/order; DTO mappers.

## Інструкції агенту

Прочитати [спільні правила](README.md#правила-виконання), [архітектуру](../architecture.md) і [DTO-специфікацію](../dto-architecture.md).

1. Реалізувати списки/detail/create/PUT draft, replace photos та обмежене видалення під чинним ADMIN/BFF.
2. Застосовувати expectedVersion до кожної зміни й атомарно збільшувати draftVersion; узгодити версію photos з історією.
3. Валідувати media ownership/ready refs, duplicates, ordering, contacts, slug uniqueness; incomplete draft дозволений. Union cover+photos — максимум 10 unique mediaId; перевіряти при обох видах зміни. Немає загального ліміту бібліотеки в 10 або 21 фото.
4. Зберігати існуючий published snapshot недоторканим при редагуванні. Відмову прав і version conflict не маскувати.

## Критерії приймання

- [ ] Чужі/невідомі ID, дублікати та stale versions обробляються визначено.
- [ ] Редагування чернетки не змінює публічні дані.
- [ ] Порядок і видалення розміщення фото не залежать від позицій у глобальних масивах.
- [ ] Історія приймає 1..10 фото, 11-те відхиляється атомарно; інші історії можуть додавати нові фото без загальної квоти.

## Перевірка

Виконати цільові перевірки поведінки, зазначені вище, та lint/typecheck/build змінених частин згідно зі спільними правилами. Записати команди, результат і невиконані критерії. Залежні наступні тікети не є виконаними фактом завершення цього.

### Поточний запис виконання (2026-11-21)

- Додано ADMIN endpoints і BFF для списків/деталей/створення/повного PUT сервісів та історій, заміни фото, settings/home draft і обмеженого видалення.
- Усі редагування використовують спільний persistence fence і `expectedVersion`; видалення також вимагає очікувану версію. Slug не змінюється після публікації; конфлікт унікальності slug повертає 409.
- Перевіряються READY-стан та власник для кожного media reference, існування service/story placement refs, унікальність контактів/вибраних IDs через DTO та SQL, ліміт 10 для обкладинки разом з фото. Видалення дозволене тільки неопублікованому контенту без refs.
- Draft writes не оновлюють `PortfolioPublishedDocument`; snapshots залишаються незалежними. Списки мають cursor, обмежений підписом, типом ресурсу й `contentVersion`.
- Згенеровано актуальні OpenAPI/TypeScript контракти. **Перевірки:** backend lint/typecheck/build, frontend lint/typecheck/production build, `portfolio:contracts:check` і `git diff --check` пройшли. Production build вимагав дозволу на запис у `.next`; є попередження Next.js про кілька lockfiles. Тести не запускалися; реальна тестова PostgreSQL не перевірена. Не закривати критерії приймання до цільових unit/integration/E2E та DB перевірок.
