# PF-CONTENT-09 — Імпорт поточного контенту та кероване перемикання

**Статус:** реалізовано та перевірено локально. Фактичне перемикання сайту і видалення FILE — окремий крок після приймання. **Область продукту:** лише портфоліо.
**Залежності:** PF-CONTENT-08; весь поточний демоконтент дозволений для MVP, реальні матеріали не блокують цей крок. Порядок і посилання — у [індексі](README.md).

## Мета та область роботи

Локальний імпорт із [маніфеста v1](../demo-import.v1.json), публікація демо та перевірка перемикання FILE/DB. Команди імпорту й відкату — у [runbook](../demo-import-runbook.md).

## Інструкції агенту

Прочитати [спільні правила](README.md#правила-виконання), [архітектуру](../architecture.md) і [DTO-специфікацію](../dto-architecture.md).

1. Інвентаризувати всі поточні тексти, ціни, services/story mappings, hero, featured та slug; зробити explicit stable mapping.
2. Створити dry-run та idempotent import у draft з manifest/checksums; повтор не дублює записи й не перетирає ручні зміни без явного режиму.
3. Зберегти шість /stories slug; імпортувати всі 21 унікальних демофото Unsplash у наше storage через PortfolioMedia pipeline. Взяти IDs/розподіл з [media-inventory.json](../media-inventory.json); hero та фон повторно використовують вже імпортовані mediaId. Зафіксувати provenance/demo marker, idempotent source mapping та перетворення великих source-файлів до дозволеного входу без прихованого пропуску.
4. Перевірити DB-mode локально, паритет контенту та послідовність service→story→settings publish. Текстові контактні заглушки перенести без вигаданих активних адрес. Demo можна опублікувати локально для MVP; реальне наповнення відбувається через готову адмінку наприкінці.
5. Описати rollback FILE/DB зі збереженням записів/об’єктів; після приймання прибрати тимчасовий flag і hardcoded runtime джерело окремим reviewable кроком, зберігши імпортований у БД демоконтент до його редакторської заміни.

## Критерії приймання

- [x] Dry-run не мутує дані; повтор імпорту не створює дублів.
- [x] Slug, тексти, ціни, добірки й порядок співставлені; імпорт містить 21 унікальне медіа без зайвих дублів від головної.
- [x] Нова тестова історія приймає 22-ге медіа в бібліотеці. 10 унікальних кадрів з обкладинкою зберігаються, 11 відхиляються з HTTP 400, а раніше збережені дев’ять фото лишаються в історії.
- [x] Локальне перемикання й відкат перевірені. Демо доступне без реальних контактів. Обмеження стенда зафіксовано нижче.

## Перевірка

- `portfolio:import-demo -- --dry-run` перевірив маніфест і повторив перевірку з підготовленими файлами. Усі 21 оригінал пройшли перевірку SHA-256 без зменшення розміру.
- `--apply` створив 21 медіа, 6 чернеток напрямів, 6 чернеток історій і чернетку головної. `--apply --publish` створив 13 опублікованих знімків після перевірки чернеток. Наступний запуск використав усі 21 готове медіа та створив 0 записів.
- Перевірено HTTP 200 для головної та шести історій у двох мовах, 14 URL у sitemap, три окремі фото добірок і BFF-редирект із завантаженням WebP. Після перезапуску в режимі FILE повернулися файлові головна й історія, API й фото з локальної БД лишилися доступними.
- PostgreSQL пройшла `prisma:deploy`. Образ MinIO не вдалося отримати, тому для локального smoke використано тестовий S3 endpoint із пам’яттю процесу. Перевірка реального S3 та перемикання сайту потребують окремого приймання.
- Backend `lint`, `typecheck`, `build`, `portfolio:contracts:check`, 101 unit, 6 persistence integration і 8 HTTP E2E. Frontend `lint`, `typecheck` і production build через `npm --prefix frontend run build -- --webpack`. Початкова збірка Turbopack у пісочниці зупинилася на етапі компіляції.
