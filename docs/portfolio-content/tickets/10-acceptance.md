# PF-CONTENT-10 — Наскрізна перевірка та закриття перетинів техборгу

**Статус:** локальне приймання виконано з відкритими зовнішніми перевірками. **Область продукту:** лише портфоліо.
**Залежності:** PF-CONTENT-09. Порядок і посилання — у [індексі](README.md).

## Мета та область роботи

Наскрізне приймання DB-портфоліо, регресії галерей, вимірювання та фактичні статуси пов’язаних тікетів.

## Інструкції агенту

Прочитати [спільні правила](README.md#правила-виконання), [архітектуру](../architecture.md) і [DTO-специфікацію](../dto-architecture.md).

1. Виконати матрицю create→upload→edit→preview→publish→read→edit again→archive; перевірити races/version conflict і failure paths.
2. Перевірити public data leakage, media lifecycle/TTL, 404/503, новий slug без rebuild, 1..10 кадрів історії без pagination та відхилення 11-го та draft isolation.
3. Запустити релевантні auth/private-gallery/archive регресії, Chromium/WebKit і фізичний checklist з TD-PF-10; не заявляти виконаний physical тест без пристрою.
4. Порівняти production-build performance з TD-PF-11: Redis cold/miss/hit, immediate publish/archive visibility, failed invalidation/retry, restart recovery, PostgreSQL fallback при відмові Redis та відсутність впливу на BullMQ. Перевірити імпорт 21 фото, додавання нових і responsive WebP 480/960/1600 на повільній мережі. Redis — умова приймання, а не опційний наступний тікет.
5. Оновити фактичні статуси TD-PF-01/02/03/04/07/09/12 і початкових 05/09; позначати лише підтверджені критерії. TD-PF-05/06/08/10/11 не закриваються автоматично.

| `npm --prefix backend run test:e2e` | 35 HTTP E2E у 4 suites |

| `node backend/test/portfolio-demo-acceptance.mjs` | Пройшли перевірки 21 фото, 14 URL sitemap, прямого PUT, BullMQ і Sharp, preview, публікації нового slug, гонки двох записів, ізоляції чернетки та архівації |

| `lint`, `typecheck`, `build` | Backend і frontend пройшли. Frontend зібрано через `build -- --webpack` |

У фінальному прогоні DB Next.js один раз записав `The destination stream closed early`. Усі шість сценаріїв пройшли, причина цього запису лишилася непідтвердженою.

Наскрізний сценарій використовує справжні PostgreSQL, Redis, Sharp і HTTPS fixture у RAM. Нова історія відображає обкладинку й дев’ять фото без пагінації, одинадцятий кадр повертає 400. Публічний JSON не повертає storage keys, власника або підписані URL. Оригінал завантажується безпосередньо в storage. BFF видає no-store редирект до WebP 480/960/1600, а після архівації нові запити до історії та її унікального медіа отримують 404. Для раніше підписаного URL перевіряється параметр TTL. Валідацію підпису й прострочення має перевірити реальне сховище.

Production build із `FILE` міг пререндерити порожній sitemap й віддавати його після перемикання на `DB`. Тепер sitemap читає режим і `APP_URL` на запиті. Та сама збірка повернула 14 URL у DB і 7 URL разом із файловою головною у FILE. Тест WebKit до гідратації тепер чекає лише потрібний шрифт, бо загальне `document.fonts.ready` чекало навмисно затримані скрипти.

### Redis і production build

HTTP-вимірювання з PowerShell на loopback, три виміри на маршрут, медіани. Перший запит після `UNLINK portfolio:public:v1:<версія>` до виділеного Redis дає cold, наступний — warm. Під час `CLIENT PAUSE 800 ALL` API читає PostgreSQL. Розмір відповіді й contentVersion збігалися в кожному режимі.

| Маршрут API, locale en | Cold, мс | Warm, мс | PostgreSQL fallback, мс | JSON, байт |
| --- | ---: | ---: | ---: | ---: |
| `home` | 35,1 | 31,5 | 251,0 | 12 986 |
| `stories/love` | 28,3 | 27,1 | 243,5 | 6 270 |

Cache integration окремо перевірила один SELECT на warm hit, відновлення outbox після перезапуску, immediate publish/archive, обробку зіпсованого запису, відмову PostgreSQL із 503 і збереження ключа BullMQ під час інвалідації. Worker також прийняв і обробив нове фото у наскрізному сценарії. Це локальні виміри для демо. Вони включають накладні витрати HTTP-клієнта.

### Браузерні метрики

`node frontend/test/portfolio-perf.mjs` — Chromium 156.0.8078.4, Next 16.3.4 (Webpack), Node 24.15.0, Windows на Ryzen 7 7700. Збірка на базі `aecf7fd` зі змінами PF-CONTENT-10. Три прогони кожної комбінації, холодний браузерний кеш, локальний Redis і медіа з HTTPS fixture. Desktop — 1440×900, 10 Мбіт/с, 20 мс затримки, CPU 1×. Mobile — 390×844, 1,6 Мбіт/с, 150 мс затримки, CPU 4× уповільнення.

Байти — передані ресурси до `networkidle`. Ліниві фото поза початковим viewport можуть завантажитися пізніше. LCP і CLS охоплюють початкове відкриття, а не повну сесію. Інтерактивність перевірено через відкриття меню та бронювання в Playwright. Польових INP і VPS-метрик у цьому запуску немає.

Для повтору на тих самих демоданих, маршрутах і профілях варто перевіряти приріст медіани LCP понад 20% чи CLS понад 0,01, а також приріст JS або фото понад 20%. Поріг LCP залишає запас над спостереженим розкидом. Це орієнтири для порівняння повторів, зокрема для перевірки desktop-обсягу фото історії. Фіксувати їх як CI-пороги варто після повторного заміру.
