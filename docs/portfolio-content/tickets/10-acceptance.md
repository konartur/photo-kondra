# PF-CONTENT-10 — Наскрізна перевірка та закриття перетинів техборгу

**Статус:** Backlog; не реалізовано. **Область продукту:** лише портфоліо.
**Залежності:** PF-CONTENT-09. Порядок і посилання — у [індексі](README.md).

## Мета та область роботи

Contract/integration/E2E suites; documentation; original tickets.

## Інструкції агенту

Прочитати [спільні правила](README.md#правила-виконання), [архітектуру](../architecture.md) і [DTO-специфікацію](../dto-architecture.md).

1. Виконати матрицю create→upload→edit→preview→publish→read→edit again→archive; перевірити races/version conflict і failure paths.
2. Перевірити public data leakage, media lifecycle/TTL, 404/503, новий slug без rebuild, 1..10 кадрів історії без pagination та відхилення 11-го та draft isolation.
3. Запустити релевантні auth/private-gallery/archive регресії, Chromium/WebKit і фізичний checklist з TD-PF-10; не заявляти виконаний physical тест без пристрою.
4. Порівняти production-build performance з TD-PF-11: Redis cold/miss/hit, immediate publish/archive visibility, failed invalidation/retry, restart recovery, PostgreSQL fallback при відмові Redis та відсутність впливу на BullMQ. Перевірити імпорт 21 фото, додавання нових і responsive WebP 480/960/1600 на повільній мережі. Redis — умова приймання, а не опційний наступний тікет.
5. Оновити фактичні статуси TD-PF-01/02/03/04/07/09/12 і початкових 05/09; позначати лише підтверджені критерії. TD-PF-05/06/08/10/11 не закриваються автоматично.

## Критерії приймання

- [ ] Є результати сценаріїв, команд і незакритих зовнішніх блокерів.
- [ ] Контракти, документація та runtime відповідають одне одному.
- [ ] Перенесення контенту завершене тільки за виконаних критеріїв; незавершені частини явно залишені відкритими.

## Перевірка

Виконати цільові перевірки поведінки, зазначені вище, та lint/typecheck/build змінених частин згідно зі спільними правилами. Записати команди, результат і невиконані критерії. Залежні наступні тікети не є виконаними фактом завершення цього.
