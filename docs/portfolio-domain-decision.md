# Портфоліо й Photo Cloud на одному домені

**Статус.** Рішення зафіксовано для першого публічного запуску. Проєкт працює локально. Підготовку хостингу й тестового HTTPS виконуємо в [тікеті 06](tickets/06-https-ingress-and-storage.md). Публічний домен обираємо під час [фінального деплою](tickets/08-launch-and-smoke-check.md).

## Розміщення та маршрути

Розгортаємо портфоліо в наявному Next.js разом із Photo Cloud. Цільова схема використовує Nginx як публічний ingress з HTTPS на зовнішньому рівні. Якщо production вже розгорнуто й хостинг підтримує цю схему, використовуємо його. Базовий варіант для першого розгортання — один керований сервер із Nginx, Next.js і NestJS у приватній мережі. Конкретний сервер або провайдер ще не підтверджено. Якщо TLS завершує балансувальник хостингу, Nginx приймає трафік лише від цього довіреного рівня і відновлює IP клієнта за правилами з README.

| Публічний шлях | Що обслуговує Next.js |
| --- | --- |
| `/` | Головна PhotoKondra |
| `/stories/[slug]` | Публічна історія. Slug-и `love`, `portrait`, `family`, `events`, `brand`, `pets` |
| `/g/[token]` | Приватний альбом |
| `/login`, `/auth/refresh`, `/dashboard/*` | Вхід, поновлення сесії та адмінка |
| `/api/*` | Наявні серверні маршрути Next.js для Photo Cloud |

Next.js звертається до NestJS за внутрішнім `API_URL`. Nginx маршрутизує запити до Next.js через `FRONTEND_UPSTREAM`. Залишаємо чинну перевірку довіреного ingress і BFF. На запуску розміщуємо оптимізовані й погоджені до публікації файли в `frontend/public/portfolio/`. Приватні альбоми й архіви залишаються в наявному приватному S3 з підписаними URL. Місце публічних файлів потрібне для тікетів 02–05.

Канонічні адреси історій використовують `/stories/[slug]`. Для шести відомих `/#story/<slug>` закладаємо клієнтську сумісність на головній із заміною адреси на канонічну. Фрагмент URL обробляє Next.js у браузері, оскільки ingress його не отримує. Звичайні якорі головної працюють як у макеті.

## Канонічний хост і видані посилання

| Що підтвердити | Стан |
| --- | --- |
| Канонічний HTTPS-хост і цільове розміщення | Обрати в тікеті 06 |
| Чинне розміщення Photo Cloud | Локальне, без публічного деплою |
| Попередні публічні хости | Відсутні для першого запуску |
| Доступ до DNS/TLS | Підготувати після вибору домену в тікеті 06 |

Перший запуск не потребує перенаправлення зі старого production-хоста. Якщо до моменту запуску вже з'являться публічні посилання, перевіряємо їхні первісні URL. За незмінного хоста вони проходять через ingress за тим самим шляхом. У разі зміни хоста старий HTTPS-хост має обслуговувати `/g/<token>` тимчасовим перенаправленням на фіксований канонічний хост зі збереженням шляху й токена та з `Cache-Control: no-store`. На старому маршруті діють ті самі обмеження на журналювання URL з токенами. За наявності розісланих URL без контролю їхнього хоста або TLS запуск блокується до погодженого способу зберегти доступ.

Підтримку старого хоста та продовження TLS забезпечує призначений оператор, доки є чинні видані з нього посилання. Для посилань без дати закінчення підтримку плануємо без фіксованої кінцевої дати. Перелік хостів уточнюємо з оператором або з наявних повідомлень із посиланнями. База зберігає хеш токена й дані доступу, тому з неї не можна відновити розісланий URL або його origin.

## Перемикання й відкат

1. До зміни DNS підготувати HTTPS, ingress, `APP_URL`, `CORS_ALLOWED_ORIGINS` і CORS S3 для цільового хоста. Зафіксувати попередню конфігурацію. Якщо є попередній публічний хост, перевірити виданий до перемикання контрольний URL і зберегти потрібні CORS-правила, доки цей хост напряму обслуговує клієнтів.
2. Перевірити обидві частини на передрелізному середовищі. Потім підключити канонічний домен і перевірити його HTTPS. За наявності старого хоста лише після цього ввімкнути сумісність на ньому. `APP_URL` задає хост нових посилань. При перемиканні чинного середовища зберігаються записи `GalleryAccess` з їхніми строками й відкликанням.
3. На production перевірити новий URL, прев’ю, оригінал і ZIP, а також відмову за відкликаним або простроченим URL. Якщо до перемикання вже видавали публічні URL, додатково відкрити той самий альбом за первісною адресою контрольного посилання. Перевірки виконуються в тікетах 06–08.
4. Якщо зламався доступ до альбомів або основний сценарій Photo Cloud, відновити попередню робочу конфігурацію ingress/DNS, налаштування origin і маршрут старого хоста. Якщо під час перемикання вже видавали посилання на новому хості, зберегти його HTTPS і маршрут `/g/*` до робочого Photo Cloud. Після відкату перевірити обидві групи виданих посилань.

## Звірка з репозиторієм

- [Шаблон Nginx](../infra/docker/nginx/frontend.conf.template) спрямовує всі шляхи до Next.js і встановлює службові заголовки ingress. Опис [production CORS](production-cors.md) і [README](../README.md) визначають окремі налаштування застосунку та S3.
- [Серверний клієнт Next.js](../frontend/lib/auth/server.ts) читає `API_URL`. [GalleryAccessService](../backend/src/gallery-access/gallery-access.service.ts) формує нові URL із `APP_URL` і перевіряє чинність посилання за хешем токена, активністю та строком дії.
- Фактичні DNS, сертифікати, мережа production і доступність старих URL підлягають підтвердженню на реальному середовищі.
